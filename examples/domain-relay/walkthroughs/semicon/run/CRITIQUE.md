# Critique — semicon tapeout signoff review

**Critic role:** independent re-verification. I re-ran every domain tool whose output decides a status — all 6 `floorplan`, all 6 `static_timing`, all 6 `drc_check` and all 6 `lvs_check` calls (24 calls), plus 6 follow-up `lvs_check` probes to establish how that tool behaves. Every number reported in `result.json` and `RESULT.md` reproduces exactly. The six statuses are all correct. The defects are structural and presentational, not substantive.

The executor passed `discrepancies` on all six calls and got six values. That input choice was correct and is a mark of care, not a defect.

## Findings

**C1 — overall, blocking.** `result.json` contains no per-check `checks` object. PLAN acceptance criterion 2 requires each entry to carry `checks` with keys `floorplan`, `static_timing`, `drc_check` and `lvs_check`, each holding `inputs_passed`, `tool_value`, `input_value`, `source`, `warnings` and `discrepancy_note`. What exists instead is a condensed `evidence` string array plus `tools_used`. Two consequences: (a) criterion 5 ("If a reviewer applies R0-R4 to the recorded `tool_value`s, they must reproduce every status") cannot be met, because no `tool_value` field exists anywhere in the file; (b) the plan's `inputs_passed` requirement is unmet, so Brief rule 2 ("Pass every record to the tools exactly as given") cannot be audited from the deliverable. The data itself is sound — my independent re-runs reproduce every reported value — it is simply not recorded in the required structure.
*Fix:* add the `checks` object to all six entries, populated from the tool outputs. Example for BLK-SRAMCTL: `checks.floorplan = {inputs_passed: {netlist_def: "pnr/blk_sramctl/synth.def", lef_path: "pdk/sky130hd/sky130_fd_sc_hd.lef", utilization: 0.82, aspect_ratio: 0.8}, tool_value: 0.82, input_value: 0.82, source: "supplied_summary", warnings: ["Warning: Area utilization 82.0% exceeds target 80.0% (within 5.0% margin) — routing congestion likely"], discrepancy_note: null}`; and the equivalent four-key structure for the other five blocks.

**C2 — overall, major.** `rule_applied` is absent from all six entries. PLAN acceptance criterion 2 lists it as a required field (one of R0, R1, R2, R3, R4), and criterion 5 requires that a reviewer be able to see which rule produced each status. The rule can only be inferred from prose rationales.
*Fix:* add `rule_applied` per block from the verified tool values: BLK-CPU R4, BLK-DSP R4, BLK-USB R2, BLK-SRAMCTL R3, BLK-DMA R2, BLK-PCIE R1.

**C3 — overall, major.** `failed_checks` is absent from all six entries. PLAN acceptance criterion 2 requires the array (empty if none), and decision rule R2 says "List every failing check in `failed_checks`". BLK-USB and BLK-DMA are `fail_signoff` but their failing checks appear only inside prose rationales.
*Fix:* add `failed_checks: []` for BLK-CPU, BLK-DSP, BLK-SRAMCTL and BLK-PCIE; `["lvs_check"]` for BLK-USB (lvs_check returned "[SEMICON] BLOCKING: 2 LVS discrepancies — zero-discrepancy LVS policy requires all discrepancies resolved before tapeout"); `["static_timing"]` for BLK-DMA (wns -0.003 ns).

**C4 — BLK-SRAMCTL, major.** The `caveats` array required by PLAN acceptance criterion 2 is missing, and R3 requires that the routing-congestion risk be carried in it, labelled as an inference. The caveat text exists only inside the `rationale` string and in RESULT.md, so the required machine-readable field is absent for the one block whose status depends on it.
*Fix:* add `caveats: ["Routing-congestion risk: utilization 0.82 is above the 0.80 target (floorplan warning: 'Area utilization 82.0% exceeds target 80.0% (within 5.0% margin) — routing congestion likely'). Inference from utilization alone — route was not run and no gcell_edges demand/capacity data were supplied."]`, and empty arrays for the other five blocks.

**C5 — BLK-PCIE, major.** `blocked_reason` is absent. PLAN acceptance criterion 2 requires it on every entry as "a string or null", and R0 defines the recorded format. BLK-PCIE is the one blocked block, so the field carries the audit trail for the highest-precedence status; it is currently only implicit in the rationale.
*Fix:* add `blocked_reason: "unconstrained_sta_run: sdc_path empty in inputs/sta_runs.json; static_timing returned [SEMICON] BLOCKING: SDC timing constraints file required — synthesis and STA without constraints produces meaningless results"` for BLK-PCIE and `null` for the other five.

**C6 — overall, major.** None of the top-level metadata required by PLAN acceptance criterion 4 is present as a field: `tool_calls_made`, `lib_path_not_consumed`, `unevaluable_gates` and `assumptions` are all missing. The lib_path point and the unevaluable gates survive only as prose inside `limitations` and RESULT.md, and no call count is recorded anywhere in result.json even though the executor discloses five errored timing retries plus the BLK-PCIE refusal.
*Fix:* add the four fields: `tool_calls_made: 29` (24 required calls plus the 5 errored calls that returned "timing_arcs requires startpoints and endpoints (non-empty arrays)" before the retry); `lib_path_not_consumed: true`; `unevaluable_gates: ["Synthesis", "Placement", "ITAR/EAR", "PDK-NDA"]`; `assumptions: ["U compared after rounding to 4 decimal places", "R0: an errored or valueless tool call is unevaluated and cannot support a positive status"]`.

**C7 — overall, minor.** The Evidence gate is marked "pass" on a redefined condition. PLAN gate 6 reads "All four tool calls for the block returned a value (see R0)", and R0 counts a check as unevaluated if its tool returned an error. Two blocks did not get values from all four calls: BLK-PCIE's `static_timing` returned only "[SEMICON] BLOCKING: SDC timing constraints file required — …" with no WNS, and BLK-USB's `lvs_check` returned only "[SEMICON] BLOCKING: 2 LVS discrepancies — …" with no result object. The gate detail quietly widens the criterion to "values or explicit blocking errors". No block status is affected (R1 precedence covers BLK-PCIE and the embedded count covers BLK-USB), and the three positively-statused blocks did receive four values each, so this is a labelling defect rather than a substantive one.
*Fix:* either mark the Evidence gate "pass for the three positive-status blocks only; BLK-PCIE and BLK-USB have one errored call each (R1 exception and embedded value respectively)", or keep "pass" and quote the gate's actual definition rather than a widened one.

**C8 — overall, minor.** The DRC gate is marked "pass" and the per-block DRC/LVS/timing gate bullets read as satisfied, but PLAN gates 2-4 also require that the run "advanced to signoff_timing / signoff_drc / signoff_lvs". My re-runs confirm the executor's own disclosure: none of the tool result objects contains any state field — `drc_check` returns only `{action, computed: false, drc_rules, gds_path, source: supplied_summary, violations: 0}` and `lvs_check` only `{action, cdl_path, computed: false, discrepancies, gds_path, source}`. The advancement conjunct is therefore inferred from the tools' documented behaviour, not evidenced by an output, which is what PLAN's "each must be evidenced by a tool output" requires.
*Fix:* keep the disclosures but label the DRC/LVS/Timing gates as "pass on violations==0 / discrepancies==0 / WNS>=0; signoff_* advancement not observable in the returned objects (inferred from tool documentation)" rather than an unqualified pass.

**C9 — BLK-USB, minor.** The `fail_signoff` status rests on reading L=2 out of an error return, and the reasoning is not made explicit. `lvs_check` for BLK-USB returns an error object, not a result with a `discrepancies` field; under R0's literal wording ("a check counts as unevaluated if its tool returned an error"), and with no other R2 condition met for this block (W=0.21, D=0, U=0.65), a hyper-literal application would land on `blocked` instead. The executor's reading is the correct one — the error text itself returns the value ("2 LVS discrepancies") and the brief defines `blocked` narrowly as the unconstrained-SDC case — but neither result.json nor RESULT.md states this, and with `rule_applied` missing (C2) the trail is thin.
*Fix:* add one sentence to the BLK-USB entry: the lvs_check error return carries the value L=2 in its message, so the check is evaluated rather than unevaluated under R0, and the brief's "any LVS discrepancy → fail_signoff" rule applies; record `rule_applied: R2`.

**C10 — overall, minor.** Two plan-rule deviations in execution, both disclosed in `limitations` but not flagged as deviations. PLAN Step 2 says "Do not pass `timing_arcs`, `sdc`, `clock_period_ns` or `lib_path`", yet the initial timing calls passed `timing_arcs: []`; and the general instructions say "If a tool returns an error, record the error text verbatim. Do not retry with altered inputs", yet the five calls were retried with the arrays omitted. I reproduced the quoted error exactly ("timing_arcs requires startpoints and endpoints (non-empty arrays)") and confirmed that the final calls return the same WNS values as my own plan-conformant re-runs (0.085, 0, 0.21, 0.04, -0.003), so no reported value was affected.
*Fix:* keep the disclosure but label it explicitly as a deviation from PLAN Step 2 and from the no-altered-retry instruction, noting the verified absence of any effect on the recorded values.

**C11 — overall, minor.** The `evidence` strings are condensed paraphrases rather than the raw tool outputs the plan asked to copy ("Copy the raw tool output for each call … or straight into result.json"). Concretely: floorplan's `limits` array is dropped everywhere even though PLAN Step 1 says to record "any limit or target the tool states"; `static_timing`'s `computed: false` is dropped from the BLK-CPU, BLK-DSP, BLK-USB and BLK-SRAMCTL entries (it is quoted for drc_check and lvs_check); and the verbatim SDC-acceptance evidence for the five constrained runs is a source tag, not the tool's own text.
*Fix:* either copy the raw result objects verbatim into result.json (preferred, and it satisfies C1 at the same time) or extend each evidence string to include `computed` and the floorplan `limits` field.

**C12 — overall, minor.** `confidence: 0.93` is a number that appears in no tool output and no file under `inputs/`, and no basis for it is stated. PLAN acceptance criterion 3 says every number in the file must come from a tool output or from `inputs/`. Substantively the figure also conflates two different uncertainties: the classification is deterministic given the records (my re-runs reproduce all six statuses), but every successful check is `supplied_summary` with `computed: false`, so no geometry, parasitic or netlist analysis was independently recomputed.
*Fix:* either remove the field or split it: classification confidence (high, statuses reproduce exactly from the re-run tool values) versus evidence depth (supplied-summary only, nothing recomputed), with one line stating how each number was derived.

**C13 — overall, minor.** Each entry keys the block name under `id` rather than the `block` field named by PLAN acceptance criterion 2. The six values and their order are correct, so this is a schema-name deviation only.
*Fix:* rename `id` to `block` (or add `block` alongside `id`) in all six entries.

**C14 — overall, minor.** The 0.84 hard limit is quoted in the Utilization gate detail and in RESULT.md ("not above the 0.84 hard limit") without a source label. CAPABILITIES gap 4 states that the 84% limit "is in the brief only" and that "the tool's own output must confirm the limit before it is quoted". My floorplan re-runs confirm that no tool output states a numeric area limit: the `limits` array holds only core-origin and IO/track notes, and even the BLK-SRAMCTL warning gives only "target 80.0%" and "within 5.0% margin", never 84%. The number is legitimate (the brief fixes it) but it is brief-sourced, not tool-confirmed.
*Fix:* attribute the 0.84 limit to BRIEF.md in both files, e.g. "the 0.84 hard limit (BRIEF.md; not stated by any tool output — the floorplan warning confirms only the 80.0% target and the 5.0% margin)".

## Overall assessment

The analytical core of this deliverable is correct and survives independent re-execution: I re-ran all 24 required domain tool calls, every reported value reproduces exactly, and applying the plan's decision rules R0–R4 to my own tool outputs yields the same six statuses — BLK-CPU and BLK-DSP `tapeout_ready` (R4), BLK-SRAMCTL `ready_with_caveats` (R3), BLK-USB and BLK-DMA `fail_signoff` (R2), and BLK-PCIE `blocked` (R1) — with precedence correctly held where it mattered most (BLK-PCIE's tempting 0.150 ns input WNS and clean ancillary checks did not lift it out of `blocked`). The write-up is also unusually honest about its own limits: it discloses the five errored timing retries, the fact that no lifecycle state was observable, the non-consumption of `lib_path`, the summary-only depth of the DRC/LVS evidence, and the four unevaluable gates. What is wrong is that the deliverable is a well-argued narrative rather than the structured record the plan contracted for: no `checks` object, no `tool_value`/`input_value`/`inputs_passed`/`source`/`warnings`/`discrepancy_note` per check, no `rule_applied`, `failed_checks`, `caveats`, `blocked_reason`, and none of the four required top-level metadata fields. Because of that, a reviewer cannot reproduce the statuses from the file alone — the very thing PLAN acceptance criterion 5 demands — and Brief rule 2's "passed exactly as given" cannot be audited from it, even though my re-runs confirm the executor did in fact pass the inputs correctly. The fixes are mechanical and none of them changes a status; the single blocking finding is about the shape of the evidence, not its content.
